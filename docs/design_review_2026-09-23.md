## 高（先に決める）

### A1. [高] GetTimeline の仕様が2つに割れている

- 場所: 4 の「GetTimeline の仕様」
- 指摘: 見出し行に「全ユーザーの投稿を最新順に表示」と書きつつ、「使うインデックス」の欄には「フォローしているユーザーの投稿を閲覧できるタブ（Twitter と同じ仕様）」とある。前者は follows と JOIN しない全体タイムライン、後者は JOIN するフォロータイムラインで、SQL がまったく別物になる。クエリ一覧では JOIN 前提で書いているので、そちらに寄せるなら見出しが誤り。
- 論点: 今週書くのは (a) フォロー中タイムラインだけ (b) 全体タイムラインだけ (c) 両方（`GetTimeline` と `GetGlobalTimeline` の2本）。
- 態度:cをやろう
- 理由:まあ片方やれたらもう片方も余裕でしょ

### A2. [高] 「is_public = false はドメイン層でブロッキング」は成立しない

- 場所: 4 の「`is_public = false` の扱い」
- 指摘: タイムラインは「複数人の投稿を条件で絞って一覧する」読み取りで、ドメインオブジェクトを1件ずつ組み立てて弾く場所が無い。仮に全件取得してから Go 側で除外すると、非公開が多いほど無駄な行を読み、LIMIT 20 件を返すのに何件読めばいいか決まらなくなる（ページングが壊れる）。除外は SQL の WHERE でやるのが自然。
- 提案: `where p.is_public = true or p.user_id = $1`（自分の非公開だけは自分に見える）を SQL に入れる。「自分の非公開を自分のタイムラインに出すか」は決める必要がある。
- 態度:賛成
- 理由:Go側で弾いてしまうと何件取得すれば良いのかわからないで腑に落ちた

### A3. [高] ページングが未記入

- 場所: 4 の「並び順とページング」
- 指摘: 空欄のままだと SQL が書けない（LIMIT も OFFSET も決まらない）。
- 論点: (a) `limit/offset`（単純。深いページで遅い、新着が入ると重複・取りこぼし）(b) カーソル（`where created_at < $2 order by created_at desc limit $3`。高速だが同時刻の扱いに注意、`(created_at, id)` の複合キーで一意にする）。件数上限も決める（20件など）。
- 態度:bに賛成
- 理由:GraphQL使うしね

### A4. [高] 「トランザクションは要るか: 跨ぐ！」の根拠が無い

- 場所: 3-2
- 指摘: 3-3 に挙げた4〜5本のユースケースは、どれも単一集約を1回 Create/Delete するだけで、複数の集約に書き込むものが無い（CreatePost は posts に1行、FollowUser は follows に1行）。跨ぐのは「投稿したらフォロワー全員に通知を作る」のような機能で、今週の一覧には入っていない。要るとするなら、どのユースケースが何と何に書き込むのかを書く必要がある。
- 提案: 今週は Transactor を作らない（指摘16 の対応も先送り）。通知を今週やるなら 3-3 に足して、そこで初めて必要になる。
- 態度:賛成
- 理由:今週はきつい

## 中（実装中に手戻りする）

### B1. [中] 1-1 の「常に成り立っていてほしいルール」に DB の制約を書いている

- 場所: 1-1
- 指摘: 「UNIQUE制約、NOT NULL」と書いてあるが、UNIQUE は他の行を見ないと判断できないので値オブジェクトでは守れない（水曜の判断軸）。`UserName` 値オブジェクトが守れるのは「空でない」「50文字以内」「文字種」の3つ。結論（値オブジェクトにする）は正しいが、根拠が別のレイヤーのルールになっている。
- 提案: 根拠を「空でない・長さ・文字種という、値そのものだけで判定できるルールが3つあり、作成時と変更時の両方で使う」に差し替える。
- 態度:賛成
- 理由:DBで守る制約としっかり切り分けるため

### B2. [中] 1-2「コンストラクタで守るルール: テーブル users と同じで良い」が具体化されていない

- 場所: 1-2
- 指摘: テーブルの制約とコンストラクタで守るルールは一致しない。`users` には UNIQUE（DB でしか守れない）があり、逆にドメインにしかないルール（description 500文字、avatar_url が http(s)、2000文字）がある。「同じで良い」だと、実装時に何を書くか決まらない。
- 提案: `NewUser` が実際に呼ぶ検証を列挙する。例: UserName 値オブジェクト（空・長さ・文字種は UserName 側）、description が500文字以内、avatar_url が空でなければ http(s) URL かつ2000文字以内。id は内部生成なので Nil チェック不要。
- 態度:賛成
- 理由:完璧

### B3. [中] 1-3 のリポジトリに Create / FindByID が無い

- 場所: 1-3
- 指摘: メソッド一覧が「Delete, Update」だけになっている。3-3 に `CreateUser` があり、4 に `CreateUser` / `GetUserByID` / `GetUserByUsername` のクエリを書いているので、interface にも `Create` / `FindByID`（必要なら `FindByUsername`）が要る。逆に `Update` / `Delete` に対応するクエリは 4 に無い。
- 提案: 3-3 のユースケース一覧と 1-3 のメソッドと 4 のクエリを突き合わせて、3つを一致させる。今週やらないもの（Update/Delete）は「今週は作らない」と明記するか、ユースケースとクエリも足す。
- 態度:今週やらないもの（Update/Delete）は「今週は作らない」と明記
- 理由:今週やることに合わせる

### B4. [中] 1-2 の `DeleteUserAccount` が rules.md の決定と食い違う

- 場所: 1-2「状態を変える操作」
- 指摘: `docs/rules.md` に「退会は論理削除。`users.deleted_at` を足す（退会ユースケースのカードで対応）」と書いた。`DeleteUserAccount` を今週やるなら、マイグレーションで `deleted_at` を足し、全クエリに `deleted_at is null` を足し、「退会者をフォローできない」等のルールも決めることになり、今週の範囲を大きく超える。
- 提案: 今週は作らない。1-2 には「UpdateProfile のみ。退会は別カード」と書く。
- 態度:賛成
- 理由:docsに仕様を合わせる

### B5. [中] 2-2 のフィールドが SQL のまま

- 場所: 2-2「フィールド」
- 指摘: `id uuid primary key default gen_random_uuid()` と DDL が貼られているが、ここはドメインのフィールドを決める欄。Go の型で書くと、2-1 で自分が書いた「集約同士は ID で参照する」がそのまま形になる（`*user.User` ではなく `uuid.UUID`）。また id は先週の決定どおり Go 側で生成するので、DB のデフォルトは使わない。
- 提案: `id uuid.UUID` / `followerID uuid.UUID` / `followeeID uuid.UUID` / `createdAt time.Time` と書く。
- 態度:賛成
- 理由:ケアレスミス

### B6. [中] follow のドメインエラーに `ErrSelfFollow` が無い

- 場所: 2-2「ドメインエラーの一覧」
- 指摘: コンストラクタで守ると決めた「自己フォロー禁止」と「UUID未設定チェック」に対応するエラーが一覧に無い。挙がっている3つは全部リポジトリ層の翻訳先。
- 提案: `follow.ErrSelfFollow`、`follow.ErrMissingUserID` を足す。
- 態度:賛成
- 理由:必要すぎる

### B7. [中] 3-2「呼ぶもの」が引数の一覧になっている

- 場所: 3-2
- 指摘: 「呼ぶもの（順番に）」は、ユースケースが**どの関数をどの順で呼ぶか**を書く欄（この層の仕事は手順を決めることなので、ここが本体）。書かれているのは入力フィールドの一覧で、1つ上の「受け取るもの」と同じ内容になっている。
- 提案: 例: `clock()` で現在時刻 → `post.NewPostContent(body, imageURL)` → `post.NewPost(userID, content, isPublic, now)` → `postRepo.Create(ctx, p)` → 結果を返す。こう書くと「検証はドメインが済ませている」「リポジトリは最後に1回」が目で見える。
- 態度:賛成
- 理由:良いと思われる、仕様に沿っている

## 低（好み・整理）

### C1. [低] `ErrInvalidUsernameChars` が2回書かれている

- 場所: 1-2 のエラー一覧
- 指摘: 同じ名前が2行ある（26行目と31行目）。文字種を採用すると決めたなら1行に統合する。
- 態度:賛成
- 理由:言わずとも

### C2. [低] `user.ErrUserNotFound` と `follow.ErrUserNotFound` の重複

- 場所: 1-2 と 2-2
- 指摘: 同名のエラーが2パッケージにでき、さらに `post/repository.go` にも暫定の `ErrUserNotFound` がある（先週「user 集約ができたらそちらへ移す」とコメントを書いた）。3つとも残すか、`user.ErrUserNotFound` に寄せるかを決めないと、実装時に毎回迷う。
- 論点: 集約同士は互いを知らない原則からすると各パッケージが自前で持つ方が素直だが、`errors.Is` で判定する側からすると同じ意味のエラーが3つあるのは扱いにくい。
- 態度:反対
- 理由:現状でいいが、ユースケース層やAPI層は、この3つを区別する(「投稿者が存在しない」と「フォロー相手が存在しない」でメッセージを変える)

### C3. [低] username 50文字はまだ長い

- 場所: 1-2
- 指摘: 100 → 50 に直っているが、X は15文字、GitHub は39文字、Instagram は30文字。`@name` でのメンションや UI の表示幅を考えると 30 文字程度が実用的。文字種を `[a-zA-Z0-9_]` に絞るなら、日本語名は `description` 側で表現することになるので、表示名（display_name）を別に持つかどうかも将来の論点。
- 態度:じゃあ20文字にしよう
- 理由:短いほうがいいか
