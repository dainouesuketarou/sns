## スキーマ（db/migrations/000001_create_initial_tables.up.sql）

### 1. [中] posts の CHECK が空文字を弾かない

- 場所: `up.sql:17` `check (body is not null or image_url is not null)`
- 指摘: `body = ''` かつ `image_url = ''` の行はこの CHECK を通る。アプリ経由なら `toPgText` が空文字を NULL に落とすので問題ないが、この制約を入れた目的は「アプリを経由しない INSERT からも守る二重防御」だった。その目的に対しては穴がある。
- 提案: `check (coalesce(body, '') <> '' or coalesce(image_url, '') <> '')` のように空文字も「値なし」として扱う。
- 態度:賛成
- 理由:あなたの言った通り、アプリ側のバリデーションを突き抜けて空が挿入されるかもしれないし、アプリ側と仕様は当一させたい（認知負荷の点で）。

### 2. [低] CHECK 制約に名前が付いていない

- 場所: `up.sql:17`, `up.sql:38`
- 指摘: 自動命名で `posts_check` / `follows_check` になっている。posts に 2 つ目の CHECK を足すと `posts_check1` になり、エラーメッセージや将来の `drop constraint` で何の制約か分からなくなる。
- 提案: `constraint posts_body_or_image_check check (...)` のように意図が分かる名前を付ける。UNIQUE も同様。
- 態度:賛成
- 理由:やって損はないと感じている。メリットしかないと思っているのでやりましょう

### 3. [中・将来] 外部キー列にインデックスが無い

- 場所: `posts.user_id`、`comments.post_id`、`follows.followee_id`、`notifications.recipient_id` など
- 指摘: PostgreSQL は外部キーを張っても、参照側の列に自動でインデックスを作らない。「あるユーザーの投稿一覧」「ある投稿のコメント」「自分をフォローしている人」「自分宛の通知」は全部これらの列で絞るクエリなので、データが増えると全件走査になる。`likes (post_id, user_id)` の UNIQUE は `post_id` 前方一致で使えるが、`follows (follower_id, followee_id)` は `followee_id` 単独の検索には効かない。
- 提案: 今のカードの範囲外なので今すぐでなくていいが、クエリを書き始めるタイミングで `create index` を足す。
- 態度:一部賛成
- 理由:「あるユーザーの投稿一覧」「ある投稿のコメント」「自分をフォローしている人」「自分宛の通知」「あるユーザーのことをフォローしている人たち」に関してはINDEXを使って最適化したいが、「自分がいいねした投稿」は今のところ実装予定がないので不要

### 4. [低] `on delete` の挙動が未定義

- 場所: 全ての `foreign key`
- 指摘: 省略時は `NO ACTION`。ユーザーを削除しようとすると、投稿が 1 件でもあればエラーになる。「退会したら投稿も消す（CASCADE）」「退会は論理削除にして物理削除しない」など、ドメインとしての決めが必要。
- 提案: 決めるのは後でいいが、`docs/rules.md` に「未決」として書いておく。
- 態度:仕様を決める必要がありそうですね。決めましょう
- 理由:存在しないユーザーの投稿が上がってたりするのは、セキュリティの観点的によくない

### 5. [低] `created_at` に DB デフォルトが無い

- 場所: 全テーブルの `created_at timestamptz not null`
- 指摘: 「Go 側で生成する」という決定に沿ってはいるが、`default now()` を付けても Go 側で明示的に渡せばそちらが優先されるので害はない。直接 INSERT する運用（テストの `insertUser` も含む）で毎回 `now()` を書く手間が減る。
- 提案: 付けるか付けないかは方針の再確認。「アプリの時計が唯一の真実」と決めるなら付けない理由になる。
- 態度:賛成
- 理由:default now()入れた方が良さそう念の為に。go側のtimestampとのタイムラグが既知であり、許容範囲内なら良いと思っている。表記法が異なっていたり、usaかasia/tokyoとで時差による間違いなどは許せないが、アプリ側で決定した時の時刻とDB側で決定した時の自国の差分に関しては許せる限りの時差であると判断

### 6. [低] マイグレーション内の `create table if not exists`

- 場所: 全 `create table`
- 指摘: golang-migrate はバージョン番号で適用済みを管理するので、`if not exists` は本来不要。むしろ「別の定義で既にテーブルがある」状態を黙って成功扱いにして、スキーマのズレを隠す方向に働く。
- 提案: `create table` にして、存在していたら失敗させる。
- 態度:　賛成
- 理由:　変更履歴だけをバージョン管理したいため

### 8. [中] `NewPost` が `time.Now()` と `uuid.New()` を内部で直接呼ぶ

### 9. [中] `toDomain` が `NewPostContent` を通すので、`RebuildPost` の「ルールは再実行しない」と矛盾している

- 場所: `post_repository.go:54` → `post_content.go:15`

- 態度:「保存済みデータは保存時点で検証済みなので信頼する」という方針に賛成

### 14. [中] DB エラーがそのまま外に漏れる

- 場所: `post_repository.go:36`, `post_repository.go:45`
- 指摘: `ErrNoRows` だけはドメインエラーに変換しているが、それ以外（外部キー違反 = 存在しない user_id、重複キー、接続断）は `pgx` のエラーがそのまま返る。ユースケース層がこれを判別しようとすると `pgconn.PgError` を import することになり、`pgtype` を閉じ込めた意味が半分崩れる。

- 理由:リポジトリ層でしっかりドメインエラーに翻訳することで、ユースケース層における依存が外向きに向かうことが発生しないだろうということで

### 16. [低・先読み] `NewPostRepository(db DBTX)` だと 1 リポジトリが 1 接続に固定される

## 「わからない」が付いた概念のメモ（来週に持ち越す用）

会話の中で実質「わからない」だったもの。Claude Code の下書きなので、自分の言葉に直すこと。

- 複合インデックスの前方一致: `(a, b)` の B-tree は `a` 単独・`a+b` では効くが `b` 単独では効かない（電話帳は姓で引けるが名では引けない）。`follows (follower_id, followee_id)` は `followee_id` 検索に効かないので別インデックスが要る
- 外部キーとインデックス: 参照される側（PK）は自動で索引あり。参照する側（子テーブルの FK 列）は手動。貼るのは WHERE/JOIN で「手に持っている値」が入る列であって、取り出したい答えの列ではない
- EXPLAIN / EXPLAIN ANALYZE: 木構造を子から読む。`cost` は相対値、`rows` は見積もりと実測を比べる。大きいテーブルの `Seq Scan` + `Rows Removed by Filter` が大きければインデックス不足。インデックスがあっても使うかはプランナが決める。MySQL は表形式、PostgreSQL は木形式
- golang-migrate の `schema_migrations`: `version` と `dirty` の1行で管理。各 `up.sql` はその DB で1回しか走らないので `if not exists` は不要、むしろズレを隠す
- Go のゼロ値: 宣言しただけの変数に入る値。標準ライブラリは「ゼロ値で使える」設計だが、ドメインの値オブジェクトには正しいゼロ値が無く、コンストラクタ迂回の穴になる。境界での検証 + DB 制約で受ける
- pgtype 変換の行き/戻り: 行き = Go → pgtype（書き込み）、戻り = pgtype → Go（読み込み）。`Valid` フラグ（NULL）の扱いを `pgconv.go` に集約する
- トランザクションの3役: 開く（インフラの TxManager が Begin/Commit）、範囲を決める（ユースケース）、届ける（ctx 経由）。リポジトリは渡されたものを使うだけ
- `timestamptz` vs `timestamp`: `timestamptz` は「瞬間」を保存し、表示のタイムゾーンが変わるだけ。時差事故が起きるのは `timestamp without time zone`
- 退会の設計: 論理削除 + 猶予期間 → 匿名化が主流。物理 CASCADE は他人のコメントを巻き込むので避ける
- エラーの翻訳: リポジトリは pgx エラーをドメインエラーに翻訳する（型の翻訳）。文言を隠すのは API 層の仕事。`%w` を2つ使えば両方チェーンに残る
